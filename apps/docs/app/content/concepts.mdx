# Concepts

This page covers the two models the SDK is built on: how the AT Protocol handles identity and data storage, and how SkyScribe organises content on top of it.

## SkyScribe's names and the SDK's names

The SDK's API is older than SkyScribe's naming, so the same thing can have three names. Authors see the SkyScribe names in the app. The SDK and the records use the others:

| In SkyScribe | In the SDK | AT Protocol record |
| ------------ | ---------- | ------------------ |
| Publication | `Site` (`fetchSite`) | `site.standard.publication` |
| Document | `Article` (`fetchArticle`) | `site.standard.document` |
| Category | `Group` | `scribe.groups[]` on the publication |

The rest of these docs use the SDK's names. When an author talks about their "Publication", that's what `fetchSite` returns.

## AT Protocol basics

SkyScribe is built on the [AT Protocol](https://atproto.com), the same open protocol that powers Bluesky. Authors' content lives in their own Bluesky account, not on a SkyScribe server. You don't need to know the protocol in depth, but a few ideas come up constantly in the SDK.

### Handle

A **handle** is a human-readable username, for example `alice.bsky.social` or `anthonycregan.dev`. Authors use their handle to identify themselves.

Handles are convenient but **not stable**: an author can change theirs at any time. So the SDK always resolves a handle to a DID before fetching any data.

### DID (Decentralized Identifier)

A **DID** is a permanent, globally unique identifier, for example `did:plc:abc123`. If a handle is like a display name, a DID is like a passport number: it never changes.

There are two DID types you may come across:

| Type | Example | How it works |
| ---- | ------- | ------------ |
| `did:plc` | `did:plc:abc123` | Managed by the PLC directory at `plc.directory`. The most common type, used by bsky.social accounts |
| `did:web` | `did:web:anthonycregan.dev` | Derived from a domain name. The DID document is fetched from `https://{domain}/.well-known/did.json` |

Every fetch function accepts either a handle or a DID as its `author` argument. Handles are resolved to DIDs automatically.

### PDS (Personal Data Server)

The **PDS** is the server that stores an author's data. All their published content lives there. It may be a shared provider like bsky.social, or a server the author runs themselves.

The SDK finds the right PDS for any author by fetching their DID document and reading its `#atproto_pds` service entry. This happens automatically: you never need to look up a PDS URL yourself.

<Callout type="tip">
  Because the SDK resolves the PDS itself, it works for authors on any PDS, not just bsky.social accounts.
</Callout>

### Collections and AT URIs

Data on a PDS is organised into **collections**: named buckets of records. SkyScribe uses two:

| Collection | Contains |
| ---------- | -------- |
| `site.standard.publication` | Site records, one per Publication the author has |
| `site.standard.document` | Article records, drafts and published |

Each record has an **rkey** (record key) that's unique within its collection. For both collections the rkey is an opaque **TID** (e.g. `3mp4nd46xwr2h`) generated by the PDS. You never need to construct one: an article's human-readable slug is stored in the Site record (see [ArticleRef](#articleref)), not in the rkey.

A record's full address is an **AT URI**:

```
at://{did}/{collection}/{rkey}
at://did:plc:abc123/site.standard.publication/3mp4nd46xwr2h
at://did:plc:abc123/site.standard.document/3mp47vvkh342n
```

## The content model

On top of the AT Protocol, SkyScribe organises content in a simple hierarchy: a Site contains Groups, and Groups contain Articles.

### Site

A **Site** is an author's Publication: the top-level container for everything that appears on one website. It's a single record in the `site.standard.publication` collection.

A Site carries:
- Metadata: `uri` (the record's AT URI), `title`, `description`, `url` (domain), `urlPrefix` (optional path prefix), `logoImageUrl`, `splashImageUrl`
- A list of **Groups**, which hold the published articles
- A list of **ungrouped articles**: a legacy field kept for older content. Expect it to be empty (see [Publication states](#publication-states))

`url` and `urlPrefix` together define where the site's content lives:

```
url: "anthonycregan.co.uk"
urlPrefix: "blog"
→ site root: anthonycregan.co.uk/blog
→ article:   anthonycregan.co.uk/blog/{group-slug}/{article-slug}
```

When `urlPrefix` is empty, groups sit directly under the domain:

```
url: "norobots.blog"
urlPrefix: ""
→ article: norobots.blog/{group-slug}/{article-slug}
```

Authors set the domain and path prefix in their Publication's settings in SkyScribe (see [Publications](https://skyscribe.app/users-guide/authoring/publications)).

#### Looking up a Site

The SDK finds a Site by its canonical HTTPS URL. Pass the full URL as the second argument to `fetchSite`:

```ts
await fetchSite('alice.bsky.social', 'https://alice.bsky.social');
await fetchSite('anthonycregan.dev', 'https://norobots.blog');
```

Internally the SDK scans the author's `site.standard.publication` collection for the record whose URL matches. You never need to know the record's rkey.

<Callout type="note">
  Records written by older tools may also carry a `scribe.slug` field. The SDK doesn't use it: lookups work entirely from the URL.
</Callout>

### Group

A **Group** (a Category, in SkyScribe) is a named, ordered collection of articles within a Site: a section of the website. Each Group has a `slug` (its URL segment) and a `title`. Their order within the Site is significant, and authors control it in SkyScribe.

### Article

An **Article** (a Document, in SkyScribe) is a single piece of writing. All articles, draft or published, are stored in the `site.standard.document` collection. An article belongs to at most one Site at a time. It contains:
- `title`, `description`, `content` (full HTML), `textContent` (plain text), `path` (URL path), `coverImageUrl`
- `tags`: optional author-defined strings
- `contributors`: optional `ArticleContributor` credits (DID, role, display name)
- `site`: the AT URI of its Site record once published, e.g. `at://did:plc:…/site.standard.publication/3abc`
- `canonicalUrl`: the fully qualified article URL, e.g. `https://myblog.com/blog/creative-writing/my-article`
- `bskyPostRef`: the Bluesky post's AT URI and CID, if the author shared the article to Bluesky
- `publishedAt`, `updatedAt` timestamps

SkyScribe works out `path` and `canonicalUrl` from the Site's domain and path prefix, the Group's slug and the article's slug when the author publishes. Authors don't type them in.

The Site record points to its articles, not the other way round.

### ArticleRef

Fetching a Site gives you its whole article list without any extra requests, because the Site record contains **ArticleRefs**: lightweight snapshots of each article's metadata (title, slug, description, splash image, tags). Only the full `content` is left out.

That avoids N+1 fetching: render an article list from the Site record alone, then fetch individual articles on demand. The article's slug lives here, and it's what `fetchArticleBySlug` matches on.

<Callout>
  `ArticleRef` only exists in code. Authors never see it: in SkyScribe they just see their Documents.
</Callout>

## Publication states

Every article is in one of two states:

| State | Condition | What it means |
| ----- | --------- | ------------- |
| **Draft** | Exists on the author's PDS; not referenced in any Site record | The author hasn't published it yet. SkyScribe calls this a Standalone Document |
| **Published** | Referenced in a Group within a Site | It has a canonical URL on the website. Publishing assigns it to the Site and places it in a Group in one step |

The SDK returns published articles inside `site.groups[n].articles`. `fetchSite` never returns drafts: no Site record references them, so there's nothing for the SDK to find them by. (A draft's `site` field holds a link to its standalone page on Scribe Reader rather than a Site's AT URI.)

<Callout type="note">
  `site.ungroupedArticles` still exists on the `Site` type for content published before this two-state model, but nothing writes to it any more, so expect an empty array. Don't build UI around it.
</Callout>

## What the records look like

The SDK maps these fields onto its flat `Site` and `Article` types, so you rarely need the raw records. They're here for when you do.

Fields defined by the `site.standard` spec ([publication](https://standard.site/docs/lexicons/publication), [document](https://standard.site/docs/lexicons/document)) live at the top level of a record. Anything SkyScribe-specific lives inside a `scribe` object on the same record, never at the top level.

### `site.standard.publication`

| Field | Notes |
| ----- | ----- |
| `url` | Canonical site URL, e.g. `https://alice.example.com` (spec) |
| `name` | Publication name (spec) |
| `description` | Optional (spec) |
| `icon` | Optional square image blob (spec) |
| `scribe.domain` / `scribe.basePath` | Domain and optional path prefix (→ `Site.url` / `Site.urlPrefix`) |
| `scribe.title` | Display title |
| `scribe.splashImageUrl` / `scribe.logoImageUrl` | Site images |
| `scribe.groups` | The ordered Groups, each with a `slug`, a `title` and its ArticleRefs |

### `site.standard.document`

| Field | Notes |
| ----- | ----- |
| `site` | The Site's AT URI once published (spec) |
| `title` | Required (spec) |
| `path` | URL path, e.g. `/essays/a-year-of-letters` (spec) |
| `description` | Optional (spec) |
| `content` | The body, as HTML (spec) |
| `textContent` | Plain-text version of the body (spec) |
| `tags` | Optional (spec) |
| `contributors` | Optional `{ did, role?, displayName? }` credits (spec) |
| `bskyPostRef` | Set if the article was shared to Bluesky (spec) |
| `publishedAt` / `updatedAt` | Timestamps (spec) |
| `scribe.createdAt` | When the article was first created |
| `scribe.coverImageUrl` / `scribe.canonicalUrl` | Cover image source and full public URL |

Draft or published is **not** a field on the record: it depends entirely on whether a Site's `scribe.groups` references the article.

### What isn't on the PDS

SkyScribe's own hosting data (site designs, subscriptions and image library details) is kept in SkyScribe's database, not in the author's account. The SDK only ever reads the content records above, so everything it needs is public and needs no login.

## How the SDK uses this

When you call `fetchSite("alice.bsky.social", "https://alice.bsky.social")`:

1. The SDK resolves `alice.bsky.social` to a DID, using Bluesky's public handle-resolution API
2. It fetches the DID document to find Alice's PDS
3. It scans Alice's `site.standard.publication` collection for the record matching the URL
4. It returns a typed `Site` object with its Groups and ArticleRefs already filled in

The PDS URL is cached in memory for the lifetime of the page, so repeated fetches for the same author don't fetch the DID document again.
